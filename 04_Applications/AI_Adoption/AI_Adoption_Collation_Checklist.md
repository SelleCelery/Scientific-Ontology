# AI Adoption Collation Checklist

# AI導入照合チェックリスト

> Status: Application note / Practical checklist
> Scope: AI adoption, Japanese administrative contexts, municipal DX, procurement, certification, responsibility boundaries, re-collation
> Language: Japanese only; English commensuration is not planned for this release because the checklist depends on Japanese administrative, municipal, procurement, and organizational contexts.
> Claim strength: S1/S2

---

## 0. 本文書の位置づけ

本文書は、AI導入を検討・評価・説明するための実務用チェックリストである。

本文書は、Research Note `AI_Adoption_as_Synchronization_Closure.md` で整理した「AI導入は制度的同期閉鎖になりうる」という理論的診断を、日本の行政・自治体DX・公共調達・資格認定・組織運用の文脈で扱える形へ落とした応用文書である。

ここでいうAI導入とは、AIモデルそのものの性能評価だけを指さない。

AI機器、AIサービス、AI資格、協会認定、自治体DX、行政調達、地域実装、導入実績、広報、説明責任、市場参入、保守運用を含む、AIが社会へ接触する境界全体を指す。

本チェックリストは、特定の自治体、団体、協会、事業者、資格制度、製品を評価・批判するものではない。

目的は、AI導入が単なる外形的同期で閉じず、実際に判断可能性、責任境界、再照合可能性、改善可能性を増やしているかを確認することである。

本チェックリストは、現時点では日本語版のみを公開する。内容が日本の行政・自治体DX・調達・資格認定・組織運用の文脈に強く依存するため、本リリースでは英語通約版を作成しない。

## 1. 中心命題

AI導入は、AI機器を入れることではない。

AI導入は、判断可能性を維持・拡張する境界設計である。

したがって、AI導入の評価は、次の問いから始める。

* 何をAIに委ねるのか。
* 何を人間の判断として残すのか。
* どこで責任が切り替わるのか。
* どこで処理を止めるのか。
* どの残差を導入後に再照合するのか。
* 導入によって、誰の判断可能性が増えるのか。
* 導入によって、誰の判断可能性が痩せる可能性があるのか。
AIを入れたことは、成果ではない。

成果として見るべきなのは、導入によって何が可能になり、誰がよりよく判断できるようになり、どの責任境界が明確になり、どの未解決が後から再照合できる形で残されたかである。

---

## 2. 本チェックリストが扱うもの

本チェックリストは、AI導入に関する以下の観点を扱う。

1. AIである必要性
2. 判断可能性
3. 責任境界
4. データ・安全・説明可能性
5. 資格・認定・協会・流通境界
6. 公共説明・自治体DX
7. 導入後の再照合経路
8. 資源・保守・持続可能性
9. 市場参入・地域開発への影響
10. 偽閉鎖とOpen Marker
これは、調達仕様書そのものではない。

また、法令、個人情報保護、情報セキュリティ、監査、契約、会計、医療・福祉・教育等の専門基準を置き換えるものでもない。

本チェックリストは、それらの前段または補助線として、AI導入の意味と境界を確認するためのものである。

---

## 3. 本チェックリストが扱わないもの

本チェックリストは、次のものではない。

* 法的助言
* 行政監査基準
* 調達基準
* 技術標準
* セキュリティ監査
* 個人情報保護評価
* AI性能ベンチマーク
* 特定製品の採点表
* 特定団体・資格制度の認定評価
* 特定自治体・事業者への批判文書
* AI実装手順書
* 非公開ランタイム設計
必要に応じて、法務、情報セキュリティ、個人情報保護、会計、調達、業務設計、現場専門職による確認を別途行う。

---

## 4. 使い方

このチェックリストは、採用可否を機械的に決めるためのものではない。

推奨する使い方は、次の通りである。

1. 導入前の企画段階で、各項目を確認する。
2. 回答できない項目を「未照合」として残す。
3. 未照合項目を、追加調査、条件付き導入、見送り、仕様修正、契約条件、運用改善へ分岐する。
4. 導入後に、実際の残差、苦情、違和感、失敗、例外処理、保守負荷を記録する。
5. 導入後評価では、「AIを入れたこと」ではなく、「判断可能性・責任境界・改善可能性が増えたか」を見る。
---

## 5. 判定区分

各項目は、次の四段階で扱う。

| 判定          | 意味                  | 推奨対応                         |
| ----------- | ------------------- | ---------------------------- |
| OK          | 照合済み。現時点で重大な未確認はない。 | 導入条件に含める。                    |
| Conditional | 条件付きで許容可能。          | 条件、期限、再評価点を明示する。             |
| Open        | 未照合。閉じてはいけない。       | Open Markerとして記録し、追加確認する。    |
| Risk        | 導入前に解消すべきリスクがある。    | 導入見送り、仕様変更、追加調査、責任境界の再設計を行う。 |

重要なのは、Open を失敗扱いしないことである。

未照合を未照合として残せる導入は、責任ある導入である。

逆に、未照合をOKとして扱う導入は、同期閉鎖へ向かいやすい。

---

## 6. 最小10問

AI導入を検討する場合、最低限、次の10問を確認する。

1. これはAIでなければ困難な処理か。
2. AIが担う処理と、人間が担う判断は分かれているか。
3. AIの出力を、人間が確認・修正・拒否できるか。
4. 誤判定や不利益が起きた場合、責任境界は明確か。
5. 利用者、職員、住民、事業者の判断可能性は増えるか。
6. 資格・認定・協会推薦は、何を保証しているか。
7. 資格・認定・導入ルートが、新規参入を不当に狭めていないか。
8. 導入後の苦情、違和感、失敗、例外、改善要求を再照合できるか。
9. 計算資源、保守、更新、データ管理、教育コストは持続可能か。
10. 導入によって、将来の改善可能性は広がるか。

## 7. チェックリスト本体

### A. AIである必要性

| No. | 確認項目                    | 照合問い                                   | 判定 |
| --: | ----------------------- | -------------------------------------- | -- |
| A-1 | AIでなければ困難な処理があるか。       | 従来機器、既存ソフト、人手、業務改善ではなぜ足りないのか。          |    |
| A-2 | AIが担う機能が明示されているか。       | 分類、予測、生成、要約、検索、異常検知、判断支援など、何を担うのか。     |    |
| A-3 | AI部分と非AI部分が分離されているか。    | 機器やサービス全体をAIと呼んでいるだけではないか。             |    |
| A-4 | AI導入以外の代替案を比較したか。       | 業務設計、既存システム改修、職員教育、低コストツールで足りる可能性はないか。 |    |
| A-5 | AIを使うことで何が新たに可能になるか。    | 導入前後で、判断、処理、発見、説明、改善のどこが変わるのか。         |    |
| A-6 | AIであることが広報上の記号になっていないか。 | 「AIを入れた」と言うためにAI化していないか。               |    |

---

### B. 判断可能性

| No. | 確認項目             | 照合問い                            | 判定 |
| --: | ---------------- | ------------------------------- | -- |
| B-1 | AIは判断を支援しているか。   | AIが判断材料を出すのか、判断そのものを代行するのか。     |    |
| B-2 | 人間が最終判断する範囲が明確か。 | どこから先を人間の判断として残すのか。             |    |
| B-3 | AI出力を拒否・修正できるか。  | 現場職員や利用者が「違う」と言える設計か。           |    |
| B-4 | 利用者・住民が異議を出せるか。  | AI出力による不利益を受けた場合、再確認や説明要求ができるか。 |    |
| B-5 | 職員の判断力が痩せないか。    | AI導入により、現場判断がブラックボックス依存にならないか。  |    |
| B-6 | 判断負荷が本当に下がるか。    | 確認作業、責任不安、例外対応が逆に増えないか。         |    |
| B-7 | AI導入後も選び直しが可能か。  | 運用変更、設定変更、利用停止、他手段への切替が可能か。     |    |

---

### C. 責任境界

| No. | 確認項目                        | 照合問い                             | 判定 |
| --: | --------------------------- | -------------------------------- | -- |
| C-1 | AI、事業者、自治体、職員、利用者の責任範囲は明確か。 | 誰が何を担い、何を担わないのか。                 |    |
| C-2 | 誤判定時の確認責任が明確か。              | 誤判定、不利益、説明不足が起きたとき、誰が確認するのか。     |    |
| C-3 | 説明責任の主体が明確か。                | 住民や利用者へ、誰が採用理由と運用理由を説明するのか。      |    |
| C-4 | 契約上の責任と実務上の責任がズレていないか。      | 契約では事業者責任でも、現場では職員が負荷を背負っていないか。  |    |
| C-5 | AIに責任が擬似的に転嫁されていないか。        | 「AIが出したから」で人間側の責任をぼかしていないか。      |    |
| C-6 | 例外時に止める権限があるか。              | 異常、苦情、誤判定、想定外利用が出たとき、誰が停止判断できるか。 |    |

---

### D. データ・安全・説明可能性

| No. | 確認項目                  | 照合問い                                     | 判定 |
| --: | --------------------- | ---------------------------------------- | -- |
| D-1 | 入力するデータの種類は明示されているか。  | 個人情報、機微情報、業務情報、住民情報を扱うか。                 |    |
| D-2 | データの保存・利用・削除条件は明確か。   | 何を保存し、何を保存せず、いつ削除するのか。                   |    |
| D-3 | 学習利用の有無が明確か。          | 入力データがモデル学習や改善に使われるのか。                   |    |
| D-4 | 出力の根拠や限界を説明できるか。      | 利用者や職員に、どの程度説明可能か。                       |    |
| D-5 | セキュリティ確認の範囲が明確か。      | アクセス権限、ログ、外部送信、委託先、クラウド利用を確認しているか。       |    |
| D-6 | 安全上止めるべき利用が定義されているか。  | AIに任せてはいけない判断、入力してはいけない情報、禁止用途は明示されているか。 |    |
| D-7 | ハルシネーションや誤出力への対策があるか。 | 出力を事実扱いせず、確認工程を持っているか。                   |    |

---

### E. 資格・認定・協会・流通境界

| No. | 確認項目                    | 照合問い                               | 判定 |
| --: | ----------------------- | ---------------------------------- | -- |
| E-1 | 資格や認定は何を保証しているか。        | 知識、操作能力、安全管理、継続学習、責任対応のどれを保証するのか。  |    |
| E-2 | 認定基準は公開されているか。          | 認定条件、更新条件、失効条件、審査基準が説明可能か。         |    |
| E-3 | 資格取得が過度な参入障壁になっていないか。   | 地域事業者、小規模開発者、現場職員、研究者を不当に排除していないか。 |    |
| E-4 | 認定と販売経路が過度に結びついていないか。   | 品質保証ではなく流通固定として機能していないか。           |    |
| E-5 | 自治体が認定に過剰依存していないか。      | 自治体自身が機能、効果、リスク、責任境界を照合しているか。      |    |
| E-6 | 資格・認定なしでも改善提案できる経路があるか。 | 現場改善や代替案が、認定外という理由だけで排除されないか。      |    |
| E-7 | 認定団体と事業者の利害関係が説明可能か。    | 推薦、認定、販売、研修、導入支援の関係が透明か。           |    |

---

### F. 公共説明・自治体DX

| No. | 確認項目                        | 照合問い                                  | 判定 |
| --: | --------------------------- | ------------------------------------- | -- |
| F-1 | 採用理由を住民に説明できるか。             | 「AIだから」ではなく、何の課題をどう改善するか説明できるか。       |    |
| F-2 | 導入目的が広報成果に偏っていないか。          | 先進性や話題性ではなく、実際の課題解決を見ているか。            |    |
| F-3 | 議会・監査・住民説明に耐える記録があるか。       | 比較検討、リスク確認、責任分担、運用条件を記録しているか。         |    |
| F-4 | 利用者への説明文があるか。               | AIを使っていること、使っていないこと、限界、異議申立て先を説明できるか。 |    |
| F-5 | 職員向け運用ルールがあるか。              | AI出力の確認方法、禁止事項、例外対応、停止条件が明示されているか。    |    |
| F-6 | 公共性を損なう囲い込みがないか。            | 特定事業者・団体・資格制度への依存が過剰でないか。             |    |
| F-7 | 導入により行政サービスへのアクセス格差が広がらないか。 | 高齢者、障害者、外国人、デジタル弱者への影響を確認しているか。       |    |

### G. 導入後の再照合経路

| No. | 確認項目                    | 照合問い                            | 判定 |
| --: | ----------------------- | ------------------------------- | -- |
| G-1 | 導入後の評価指標があるか。           | 導入したことではなく、何が改善したかを見る指標があるか。    |    |
| G-2 | 苦情・違和感・失敗を拾う経路があるか。     | 現場職員、利用者、住民からの残差を記録できるか。        |    |
| G-3 | 例外処理を記録できるか。            | 想定外ケース、手戻り、人間判断への差戻しを記録するか。     |    |
| G-4 | 改善要求を反映できるか。            | 仕様変更、運用変更、契約見直し、停止判断へ接続できるか。    |    |
| G-5 | 定期的な再評価があるか。            | 一度導入したら固定されるのではなく、期限付きで再照合されるか。 |    |
| G-6 | 導入効果が確認できない場合の撤退条件があるか。 | 効果不明でも継続される構造になっていないか。          |    |
| G-7 | 失敗を隠さず学習資源にできるか。        | 問題発生時に、責任回避ではなく改善へ回せるか。         |    |

### H. 資源・保守・持続可能性

| No. | 確認項目                | 照合問い                                 | 判定 |
| --: | ------------------- | ------------------------------------ | -- |
| H-1 | 計算資源の負荷は妥当か。        | AIでなくてもよい処理までAI化していないか。              |    |
| H-2 | 保守・更新コストは見積もられているか。 | 導入費だけでなく、継続費用、更新費用、教育費用を見ているか。       |    |
| H-3 | 担当者交代後も運用できるか。      | 属人化せず、引継ぎ可能な運用設計か。                   |    |
| H-4 | ベンダーロックインの危険はあるか。   | 特定事業者や特定団体から離れられない設計になっていないか。        |    |
| H-5 | データ移行・契約終了時の扱いが明確か。 | 利用停止時にデータ、ログ、設定、学習成果をどう扱うか。          |    |
| H-6 | AI軽量境界設計になっているか。    | 必要な処理に必要な分だけAIを使い、余計な探索や過剰処理を避けているか。 |    |
| H-7 | 地域のAI活用能力を育てているか。   | 導入によって、地域内の学習、開発、改善能力が増えるか。          |    |

### I. 市場参入・開発多様性

| No. | 確認項目                    | 照合問い                         | 判定 |
| --: | ----------------------- | ---------------------------- | -- |
| I-1 | 導入が特定ルートを事実上の標準にしていないか。 | 自治体採用により、他の方法が排除されていないか。     |    |
| I-2 | 新規開発者が参入できる余地があるか。      | 小規模事業者、個人開発者、研究者が提案できるか。     |    |
| I-3 | 地域事業者が改善提案できるか。         | 地域課題に即した小さな改善が入り込めるか。        |    |
| I-4 | 認定外の技術や製品が検討対象に残るか。     | 認定外という理由だけで排除されないか。          |    |
| I-5 | 導入後に代替製品へ移行できるか。        | よりよい製品や方法が出たとき、切り替え可能か。      |    |
| I-6 | 市場の入口を狭めていないか。          | AI活用の普及ではなく、流通経路の固定になっていないか。 |    |

### J. 偽閉鎖とOpen Marker

| No. | 確認項目                        | 照合問い                             | 判定 |
| --: | --------------------------- | -------------------------------- | -- |
| J-1 | 「AI導入済み」で問題を閉じていないか。        | 実際には未解決の業務課題を、導入によって処理済みにしていないか。 |    |
| J-2 | 「認定済み」で能力確認を閉じていないか。        | 資格や認定があることで、実運用能力の確認が省略されていないか。  |    |
| J-3 | 「導入実績あり」で効果確認を閉じていないか。      | 他所の実績が、自地域での適合性確認を置き換えていないか。     |    |
| J-4 | 「契約上問題なし」で責任境界を閉じていないか。     | 契約と実運用の責任がズレていないか。               |    |
| J-5 | 未解決項目をOpen Markerとして残しているか。 | まだ閉じていない項目に、期限、確認者、再照合条件を置いているか。 |    |
| J-6 | Open Markerが放置されない仕組みがあるか。  | 未解決項目が、次回会議、契約更新、評価報告へ接続されているか。  |    |

## 8. 比較表：同期だけの導入と照合された導入

| 観点    | 同期だけの導入                  | 照合された導入                    |
| ----- | ------------------------ | -------------------------- |
| 採用理由  | AI機器だから、認定があるから、実績があるから。 | AIでなければ困難な支援内容が明確である。      |
| 機能    | AIと呼ばれている。               | AIが担う機能と非AI部分が分離されている。     |
| 判断    | AI出力が事実上の判断になる。          | AI出力を人間が確認・修正・拒否できる。       |
| 責任    | 事業者、自治体、資格者、AIの責任が混ざる。   | 誰が何を担うかが明確である。             |
| 資格    | 権威づけ、販売経路、参入関門になる。       | 能力保証、継続学習、利用者保護に使われる。      |
| 公共説明  | 導入実績、先進性、DX推進として説明する。    | 課題、効果、限界、異議申立て、再評価条件を説明する。 |
| 市場影響  | 既存ルートに乗る製品が有利になる。        | 新規開発者や地域改善の入口を残す。          |
| リスク管理 | 問題が起きてから対応する。            | 導入前から残差を予測し、再照合条件を置く。      |
| 資源    | AI化そのものが目的化する。           | 必要な場所に必要な分だけAIを使う。         |
| 成果指標  | AIを入れたこと。                | 判断負荷、見落とし、説明責任、改善可能性の変化。   |

## 9. 比較表：偽閉鎖された導入とOpen Markerを持つ導入

| 観点    | 偽閉鎖された導入       | Open Markerを持つ導入      |
| ----- | -------------- | --------------------- |
| 未解決項目 | 導入済みとして処理される。  | 未照合として記録される。          |
| 不明点   | 曖昧なまま進む。       | 期限、確認者、再照合条件を置く。      |
| 苦情    | 例外扱いされる。       | 残差として記録される。           |
| 現場違和感 | 習熟不足とされる。      | 仕様・運用・責任境界の再確認材料になる。  |
| 資格制度  | あるだけで安心材料になる。  | 能力保証として機能しているか再評価される。 |
| 導入効果  | 広報・実績として固定される。 | 導入後評価で検証される。          |
| 改善可能性 | 固定化される。        | 変更・撤退・再設計の余地を残す。      |

---

## 10. Open Marker 記録テンプレート

未照合項目は、次の形式で残す。

```text
Open Marker ID:
対象項目:
未照合の内容:
現時点で分かっていること:
現時点で分からないこと:
放置した場合のリスク:
確認に必要な情報:
確認担当:
再照合期限:
導入判断への影響:
次の処置:
```

例：

```text
Open Marker ID: OM-001
対象項目: AIである必要性
未照合の内容: 既存ソフト・人手・業務改善で足りる可能性が未確認。
現時点で分かっていること: 導入予定サービスは文書分類と要約を行う。
現時点で分からないこと: 既存検索システムとの比較、職員作業時間の削減効果。
放置した場合のリスク: AI導入実績のみが成果化し、実効性が不明になる。
確認に必要な情報: 比較表、試行結果、職員ヒアリング。
確認担当: 企画担当・現場担当・情報システム担当。
再照合期限: 試行導入後1か月。
導入判断への影響: 本導入前に再評価。
次の処置: 小規模試行と比較記録を実施する。
```

## 11. 導入判断の分岐

チェック後の判断は、次のように分岐する。

| 状態             | 判断        | 対応                           |
| -------------- | --------- | ---------------------------- |
| 主要項目がOK        | 導入可能      | 導入条件と再評価点を明記する。              |
| 一部がConditional | 条件付き導入    | 条件、期限、責任者、撤退条件を明記する。         |
| 重要項目がOpen      | 保留または試行   | 小規模試行、追加調査、Open Marker管理を行う。 |
| 重要項目がRisk      | 見送りまたは再設計 | 仕様、契約、責任境界、資格要件を見直す。         |
| 責任境界が不明        | 導入不可に近い   | 説明責任と停止権限が明確になるまで進めない。       |
| 再照合経路がない       | 導入不可に近い   | 導入後評価と改善経路を設計する。             |

## 12. 導入前レビュー用の短縮版

時間が限られている場合、最低限、以下だけを確認する。

| No. | 問い                      | 判定 |
| --: | ----------------------- | -- |
|   1 | AIでなければ困難な処理か。          |    |
|   2 | AIが担う処理と人間判断の境界は明確か。    |    |
|   3 | AI出力を確認・修正・拒否できるか。      |    |
|   4 | 誤判定時の責任境界は明確か。          |    |
|   5 | 利用者・住民・職員が異議を出せるか。      |    |
|   6 | 資格・認定は能力保証として機能しているか。   |    |
|   7 | 資格・認定が参入障壁になっていないか。     |    |
|   8 | 導入後の違和感・苦情・失敗を再照合できるか。  |    |
|   9 | 保守・更新・計算資源・教育コストは持続可能か。 |    |
|  10 | 導入により将来の改善可能性は広がるか。     |    |

この10問のうち、3つ以上がOpenまたはRiskである場合、本導入ではなく、試行導入、追加調査、仕様再設計を優先する。

## 13. 公開・政策提案向けの要約文

AI導入の評価は、AI機器やAIサービスを導入したかどうかだけでは不十分である。

重要なのは、その導入が、誰の判断可能性を増やし、どの責任境界を明確にし、どの未解決項目を導入後に再照合できる形で残しているかである。

AIという名称、資格、認定、導入実績、自治体支援は、導入の説明を助ける。
しかし、それらが、AIである必要性、責任境界、再照合経路、市場参入可能性、判断可能性の確認を置き換える場合、その導入はAI活用ではなく、AI導入記号による同期閉鎖へ近づく。

本チェックリストは、AI導入を否定するためのものではない。

AI導入を、より責任あるものにするための照合表である。

## 15. 最小定義

| 用語          | 定義                                          |
| ----------- | ------------------------------------------- |
| AI導入        | AI機器、サービス、資格、認定、運用、責任境界を含む、AIが社会へ接触する制度的過程。 |
| 照合          | 同期が何を意味し、何を可能にし、何を残差として残すかを読む操作。            |
| 同期閉鎖        | 外形上の導入が成立したことで、未解決の問題が処理済みとして扱われる状態。        |
| 判断可能性       | 人間が自分で考え、保留し、選び直し、拒み、再接続できる余地。              |
| 責任境界        | AI、事業者、自治体、資格者、職員、利用者が、それぞれ何を担うかの境界。        |
| 偽閉鎖         | 未解決の層が残っているにもかかわらず、処理済みとして扱われること。           |
| Open Marker | 未解決を解決済みにせず、後から再照合できるよう保持する印。               |
| 再照合経路       | 導入後に違和感、失敗、苦情、例外、改善要求を拾い直す経路。               |
| 市場参入境界      | 公共導入や認定制度によって、誰が参入でき、誰が排除されるかを決める境界。        |
| AI軽量境界設計    | 必要な場所に必要な分だけAIを使い、余計な探索・過剰処理・責任混線を避ける境界設計。  |

## 16. 要約

AI導入は、AI機器を入れることではない。

AI導入は、判断可能性を維持・拡張する境界設計である。

本チェックリストは、AI導入において、AIである必要性、判断可能性、責任境界、資格・認定境界、公共説明・自治体DX、再照合経路、資源・持続可能性、市場参入境界、偽閉鎖リスクを確認するためのものである。

導入時にすべての項目を完全に閉じる必要はない。

しかし、未照合のものを、照合済みとして扱ってはならない。

AI導入に必要なのは、導入記号ではなく照合である。

何を導入したかではなく、何が可能になったか。
誰が判断できるようになったか。
どこで責任が切り替わるか。
何を未解決として残すか。
導入後にどの残差を再照合できるか。

それらを確認するために、本チェックリストを用いる。
