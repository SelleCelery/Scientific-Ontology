## 0. 位置づけ

本文書は、存在境界論において、共有された目的を、組織境界、責任境界、ポート、プロトコル、履歴、監査、例外処理、境界更新へ実装するための横断モデルである。

本稿が所有する問いは、次の一つである。

> 目的が組織へ共有されたとき、その目的を、誰が、どの境界で、どの通信を受け取り、どの手続で変換し、どの責任境界へ返す構造として実装できるか。

本稿は、目的そのものを選ばない。

何を第一義として置き、その共有がどの世界を形成し、どの境界からの返りによって修正されるべきかは、[`Truth_Management_and_Boundary_PDCA.ja.md`](../../00_Overview/Truth_Management_and_Boundary_PDCA.ja.md) が扱う。

本稿は、認識軸を生成しない。

何が感じられ、何が理解可能になり、何が価値またはコストとして前景化するかは、[`Entropy_Attributed_Difference_and_Cognitive_Axis_Formation.ja.md`](../../02_Raj_Beauty/Entropy_Attributed_Difference_and_Cognitive_Axis_Formation.ja.md) が扱う。

本稿は、思想、世界観、学問、制度の間を直接通約しない。

異なる認識形式を、関心、捨象、価値、コスト、Core Invariant、Operational Drift、翻訳不能残差として照合する境界プロトコルは、[`Optional_Axiom_Modules_as_Cognitive_Bridge.ja.md`](../../03_Tam_Goodness/Optional_Axiom_Modules_as_Cognitive_Bridge.ja.md) が扱う。

本稿は、それらの上流文書から次を受け取る。

- 第一義と競合目的
- 対象境界
- 保存すべき履歴
- 受け入れる差分
- 期待する変換
- 社会へ返すネゲントロピー
- 許容しない外部化
- 停止条件
- 境界CAで再照合すべき項目

そして、それらを次へ落とす。

```text
目的
  ↓
組織境界
  ↓
責任境界
  ↓
ポート
  ↓
プロトコル
  ↓
履歴・監査
  ↓
例外処理・異議申立て
  ↓
境界更新
  ↓
目的への返り
```

したがって、本稿は、目的論と個別実装の間に置かれる。

それは組織を理想化する文書ではない。

組織が、どこで通信を受け、どこで責任を保持し、どこへ負荷を外部化し、どの異常から自らを更新するかを観測可能にするための文書である。

## 1. なぜ目的だけでは実装にならないのか

組織は、目的を掲げるだけでは動かない。

目的が共有されると、役割、権限、予算、評価、情報経路、例外、記録、停止条件へ変換される。

この変換が曖昧であれば、目的は現場へ届かない。

また、目的名だけが届き、責任、異議申立て、監査、停止権限が届かなければ、目的は命令またはスローガンへ変質する。

たとえば、「安全」を掲げても、事故を報告するポートがなければ安全は実装されない。

「人を大切にする」と掲げても、疲弊を記録し、配置を修正し、業務を止める責任主体がいなければ、その目的は組織境界に接続されていない。

「AIを活用する」と掲げても、入力、権限、判断、説明、例外、撤退を処理するポートがなければ、AIは組織の外部にある道具ではなく、責任の空白を内部へ持ち込む。

目的を実装するとは、目的を細かい命令へ分解することではない。

目的を、責任ある通信と修正可能な履歴へ変換することである。

## 2. 境界としての組織

組織とは、単なる人の集合ではない。

本稿では、組織を次の要素を保持する動的境界として読む。

```text
Organization
  = Boundary
  + Purpose
  + Responsibility
  + Ports
  + Protocols
  + History
  + Processing Capacity
  + Return Paths
  + Boundary Update
```

### 2.1 Boundary / 境界

何を内部として扱い、何を外部として扱うかを定める。

### 2.2 Purpose / 目的

何を受け取り、何へ変換し、何を返す組織であるかを定める。

### 2.3 Responsibility / 責任

誰が許可し、監督し、説明し、改善し、停止し、履歴を保持するかを定める。

### 2.4 Ports / ポート

どの種類の通信を、どの条件で受け入れ、処理し、返すかを定める。

### 2.5 Protocols / プロトコル

受け取った通信を、誰が、どの形式へ変換し、どこへ送るかを定める。

### 2.6 History / 履歴

過去の接触、判断、例外、失敗、修正が、次の受け取り方を変える形で保持される。

### 2.7 Processing Capacity / 処理能力

どれだけの差分、例外、矛盾、苦情、危機を、外部化せず処理できるかを定める。

### 2.8 Return Paths / 返路

出力、責任、異議、修正要求、残差が、次の処理主体または原目的へ戻る経路を定める。

### 2.9 Boundary Update / 境界更新

現行の境界、役割、権限、ポート、プロトコルでは処理できない異常を受けて、組織構造を修正する。

この定義は、企業だけを対象としない。

共同体、行政、学校、病院、研究組織、OSS、国家、国際組織、AIエージェント群も、それぞれ異なる条件を持つ境界系として比較できる。

ただし、比較可能であることは、同一であることを意味しない。

法的地位、身体性、権力、強制力、時間射程、撤退可能性、責任能力は、各境界系で異なる。

## 3. 第一義をネゲントロピー定義へ変換する

組織が何をエントロピーとして受け取り、何をネゲントロピーとして返すかは、その組織が何を第一義として置くかに依存する。

本稿では、組織の自己定義を、標語ではなく変換契約として表す。

| 項目 | 問い |
|---|---|
| 第一義 | 何を守り、増やし、失ってはならないものとして置くか。 |
| 受入差分 | どの未整理、苦痛、矛盾、危険、需要を内部で受け取るか。 |
| 変換 | 受け取った差分を、どの能力、手続、関係、意味へ変えるか。 |
| 返却価値 | 社会、利用者、構成員、自然、未来へ何を返すか。 |
| 禁止外部化 | 内部で処理すべき負荷を、誰へ押し流してはならないか。 |
| 責任主体 | 変換の成否、例外、失敗、説明を誰が引き受けるか。 |
| 時間射程 | どの期間まで後続条件を追跡するか。 |
| 停止条件 | 何が起きたら変換を停止し、目的へ戻るか。 |

病院であれば、痛み、病気、診断不能、ケア不足を受け取り、回復、説明、ケア、選択可能性を返そうとする。

学校であれば、未整理の経験、学習不能、孤立、知識不足を受け取り、理解、学習回路、共同探究、将来の行為可能性を返そうとする。

裁判所であれば、紛争、権利侵害、責任不明を受け取り、手続的公正、判断、責任処理、再発防止可能性を返そうとする。

研究組織であれば、未整理の知識、未検証の仮説、分断された知見を受け取り、検証可能性、反例、通約可能性、公開可能な知識を返そうとする。

ここでいうエントロピーとネゲントロピーは、熱力学的な量として用いるものではない。

組織が何を未整理な負荷として受け取り、何を秩序、意味、ケア、判断可能性、行為可能性として返そうとするかを読むための概念モデルである。

組織の目的は、理念文よりも、実際に何を受け入れ、何へ変換し、何を返し、何を外部へ押し流したかに現れる。

## 4. Organizational Boundary / 組織境界

組織境界とは、組織が、内部、外部、通信、責任、履歴、処理能力を定義する動的境界である。

境界は固定された壁ではない。

入力を受け入れ、保留し、遮断し、変換し、反射し、別のポートへ送る面である。

### 4.1 内部と外部

内部とは、物理的な建物の内側ではない。

その組織が、責任、処理、説明、履歴保持の対象として引き受ける領域である。

外部とは、無関係な領域ではない。

組織の処理能力、権限、目的の外側にありながら、通信、負荷、返りを交換する領域である。

### 4.2 動的境界

組織境界は、次によって変化する。

- 目的
- 法令
- 権限
- 技術
- 危機
- 社会的期待
- 構成員の能力
- 外部委託
- 合併、分割、撤退
- 失敗履歴

したがって、境界を一度定義して終えることはできない。

### 4.3 境界の曖昧化

組織境界が曖昧になると、次が起きる。

- 誰が処理するか分からない。
- 誰が説明するか分からない。
- 誰が停止できるか分からない。
- 問題が部署間を移動し続ける。
- 利益は内部化され、負荷は外部化される。
- 記録は残るが、責任主体へ戻らない。

### 4.4 境界の硬直

組織境界が硬直しすぎると、次が起きる。

- 外部の変化を受け取れない。
- 例外をすべて規則違反として処理する。
- 異議申立てを敵対として扱う。
- 内部ヒューリスティックが教義化する。
- 処理不能な差分が外部へ押し戻される。

安定した組織境界は、開放でも閉鎖でもない。

何を、どの条件で、どのポートから受け取り、どこへ返すかを区別できる境界である。

## 5. Responsibility Boundary / 責任境界

責任境界とは、行為だけでなく、その行為を許可し、設計し、監督し、説明し、改善し、停止し、履歴を保持する主体の境界である。

本稿の中心原則は、次である。

> **機能は委託できる。責任は、委託によって消すことはできない。**

外部委託、分業、自動化、AI利用は、機能の配置を変える。

しかし、配置変更それ自体は、責任を消去しない。

### 5.1 責任を構成する役割

責任は、一人の「責任者」という肩書だけで構成されない。

少なくとも次の役割に分解できる。

- **目的設定**：なぜ行うかを定めた主体
- **設計**：仕組み、指標、ポート、プロトコルを作った主体
- **許可**：実行を承認した主体
- **実行**：具体的な処理を行った主体
- **監督**：運用を観測し、異常を検知する主体
- **受益**：利益、効率、権限を得た主体
- **説明**：影響を受けた者へ理由を返す主体
- **改善**：失敗後に構造を変更する主体
- **停止**：運用を止める権限を持つ主体
- **履歴保持**：判断、例外、異議、修正を保存する主体

これらは同一主体が担う場合も、分散する場合もある。

重要なのは、分散した責任の返路が失われないことである。

### 5.2 責任洗浄を防ぐ

責任は、次のような経路で見えなくなる。

```text
発注者
  → 委託先
  → 下請け
  → 現場担当
  → 自動化システム
  → AI出力
  → 利用者の自己責任
```

この連鎖で機能が分散しても、設計、許可、利益、監督、改善の履歴は残る。

存在境界論では、責任を履歴から洗浄できないものとして扱う。

誰が許可したか。  
誰が利益を得たか。  
誰が異常を知り得たか。  
誰に停止権限があったか。  
誰が異議申立ての返路を閉じたか。

これらは、後続条件を変えた履歴として残る。

### 5.3 責任境界と法的責任

本稿の責任境界は、法的責任と同一ではない。

法的責任は、法令、契約、判例、管轄、証拠によって定まる。

責任境界は、それ以前またはそれを横断して、設計、許可、利益、監督、改善、返路をどの主体が保持していたかを問う概念モデルである。

法的結論を直接導くためには用いない。

## 6. Port / ポート

ポートとは、組織境界において、特定の種類の通信を受け入れ、変換し、処理し、返すための境界口である。

組織は、単一の入口からすべてを処理できない。

研究、営業、法務、教育、採用、財務、苦情、危機、監査、外交は、それぞれ異なる条件を必要とする。

ポートの違いは、組織内の序列を意味しない。

異なる差分を、異なる責任と処理能力で受け取る必要があることを意味する。

### 6.1 ポートの最小仕様

各ポートは、少なくとも次を持つ。

| 項目 | 内容 |
|---|---|
| Port Name | ポートの名称と対象通信 |
| Purpose | なぜこのポートが必要か |
| Accepted Input | 受け入れる差分、形式、範囲 |
| Sender / Actor | 誰が送信・利用できるか |
| Authority | 何を判断・変更できるか |
| Transformation | 入力をどの形式へ変換するか |
| Capacity | どれだけ処理できるか |
| Escalation | 処理不能時にどこへ送るか |
| Output | 誰へ何を返すか |
| Return Path | 異議、修正、追加情報をどう戻すか |
| Logging | 何を履歴として残すか |
| Stop Condition | どの条件で処理を止めるか |
| Reopen Condition | 何が満たされれば再開できるか |

### 6.2 ポートの類型

#### Service Port / 通常業務ポート

定型的な申請、相談、取引、処理を受ける。

#### Exception Port / 例外ポート

通常手続では処理できない事案を受ける。

#### Appeal Port / 異議申立てポート

判断を受けた者が、理由、再審査、修正を求める。

#### Audit Port / 監査ポート

通常運用から独立して、履歴、権限、例外、外部化を照合する。

#### Emergency Port / 緊急ポート

通常の優先順位を変更し、危機処理へ接続する。

#### Learning Port / 学習ポート

異常、失敗、改善案を、境界更新へ送る。

#### Diplomatic Port / 外交ポート

異なる組織境界の間で、相手を内部化せず通信可能性を維持する。

#### AI Port / AI接続ポート

AIが受け取れる入力、参照できる履歴、出力先、権限、停止条件を限定する。

### 6.3 ポート不在

必要なポートが存在しないと、通信は消えるのではない。

別の経路へ流れる。

- 苦情が雑談になる。
- 異常が個人の抱え込みになる。
- 例外が規則違反になる。
- 修正要求が離職になる。
- 外交が非公式な根回しになる。
- 安全上の異議が沈黙になる。

ポート不在は、問題不在ではない。

問題を観測不能にする構造である。

### 6.4 ポート過負荷

ポートに処理能力を超える入力が入ると、次が起きる。

- 待機時間の増大
- 定型応答への縮退
- 例外の切捨て
- 説明の省略
- 入力者への責任転嫁
- 非公式経路への流出
- 現場担当者の疲弊

したがって、ポート管理には、入力制御だけでなく、処理能力、待機、優先順位、保留、返却の設計が必要である。

## 7. Protocol / プロトコル

プロトコルとは、通信を受けた後、誰が、何を、どの条件で、どの形式へ変換し、どこへ返すかを定める境界手続である。

プロトコルは、単なるマニュアルではない。

マニュアルが具体的な作業手順を示すのに対し、プロトコルは、主体、権限、入力、変換、出力、例外、返路の関係を定める。

### 7.1 プロトコルの基本項目

```text
Who
  誰が受け取るか

What
  何を通信として扱うか

Under What Conditions
  どの条件で通すか、保留するか、遮断するか

Transform
  どの形式へ変換するか

Route
  どこへ送るか

Return
  誰へ何を返すか

Escalate
  誰に再判断を求めるか

Log
  何を履歴として残すか

Stop / Reopen
  何が起きたら停止し、どの条件で再開するか
```

### 7.2 権限とACLの類比

組織権限は、通信ネットワークにおけるACLと一定の通約可能性を持つ。

誰が、どのポートへ、どの操作でアクセスできるかを定める点では似ている。

しかし、組織権限は、技術的アクセス権だけではない。

法的地位、専門性、説明責任、信頼、文化、緊急性、異議申立て可能性を含む。

したがって、ACLとの対応は構造アナロジーであり、同一性ではない。

### 7.3 プロトコルの硬直

プロトコルが硬直すると、規則に適合するものだけが現実として扱われる。

分類不能な差分は、ノイズ、対象外、自己責任として外へ出される。

プロトコルは、例外をなくすためのものではない。

例外を、誰が、どこで、どの責任をもって扱うかを定めるためのものである。

## 8. Processing Capacity / 処理能力

組織境界は、無限の差分を受け取れない。

処理能力とは、単なる人員数や計算量ではない。

次を含む。

- 入力を理解する能力
- 翻訳する能力
- 例外を保留する能力
- 複数目的の競合を扱う能力
- 履歴を検索する能力
- 説明を返す能力
- 異議を再照合する能力
- 異常を境界更新へ送る能力
- 長期的な後続条件を追う能力

### 8.1 待機と保留

すぐに処理できないことと、無視することは同じではない。

成熟した組織は、保留状態を持つ。

保留には、次が必要である。

- 保留理由
- 責任主体
- 再開条件
- 再照合期限
- 入力者への説明
- 履歴保持

保留を持たない組織は、未処理を「完了」「対象外」「返答不能」へ偽閉鎖しやすい。

### 8.2 オーバーフロー

処理能力を超えた入力は、消えない。

- 現場の残業になる。
- 顧客の待機になる。
- 家族のケア負担になる。
- 自然環境への排出になる。
- 将来世代の修復費用になる。
- 説明不能なAI出力になる。

オーバーフローの送り先を観測することは、組織境界を読む上で重要である。

## 9. History, Logging, and Audit / 履歴・ログ・監査

組織は、記録があるだけでは履歴を保持しているとは限らない。

ログとは、出来事を保存した記録である。

履歴とは、その記録が、次の判断、責任、受け取り方、境界更新へ接続される構造である。

大量のログを保存しても、検索、照合、権限、改善経路がなければ、履歴として機能しない。

### 9.1 何を記録するか

少なくとも次を区別して記録する。

- 入力
- 判断
- 根拠
- 実行
- 例外
- 保留
- 異議申立て
- 再判断
- 停止
- 目的・境界・プロトコルの変更

### 9.2 監査

監査とは、規則遵守だけを確認することではない。

本稿では、次を照合する。

- 第一義と実際の運用が一致しているか。
- ポートが必要な通信を受け取れているか。
- 責任が下流へ消えていないか。
- 処理不能な負荷が外部化されていないか。
- 例外が記録され、境界更新へ届いているか。
- 異議申立てが報復なく機能しているか。
- 停止条件が実行可能か。
- 監査結果を受けて権限・目的を変更できるか。

### 9.3 監査の監査

監査系もまた、完全ではない。

同じ異常が繰り返し後から発見されるなら、対象だけでなく監査系に盲点がある。

「なぜこの種類の問題だけ記録されないのか」  
「なぜこのポートからの異議だけ重要度が下がるのか」  
「なぜ指標上は正常なのに、現場の疲弊だけ増えるのか」

これらは、監視対象の異常ではなく、観測系そのものの異常である。

成熟した監査は、対象だけでなく、自らが何を見えなくしているかを検査する。

## 10. 正常・異常・例外・境界更新

正常状態は、想定どおりに処理される状態である。

正常は重要である。

しかし、正常運用だけを観測しても、組織の限界は見えにくい。

### 10.1 正常を仕組みに委ねる

標準化、チェックリスト、自動化、マニュアルの目的は、人間が正常を見続けることではない。

正常処理を仕組みに委ね、人間の注意を、逸脱、例外、矛盾、未処理へ移すことである。

### 10.2 異常は境界情報である

異常には、少なくとも二つの側面がある。

- 破綻の予兆
- 環境変化または新しい需要の兆候

異常は、現実が現在のプロトコルに収まらなくなった地点である。

したがって、異常は排除すべきノイズである場合もあるが、境界更新の入力である場合もある。

### 10.3 成功している異常

最も見えにくいのは、成果を出している異常である。

- 特定個人の抱え込み
- 暗黙知への依存
- 残業による吸収
- 善意による例外処理
- 利用者による自己補完
- 外部環境への負荷転嫁

成果指標が良好であるため、異常として認識されない。

しかし、支えていた偶然が失われた瞬間に崩壊する。

成功している異常は、拡大前に照合しなければならない。

### 10.4 Boundary Update / 境界更新

境界更新は、次の循環で行う。

```text
正常処理を仕組みに委ねる
  ↓
逸脱・異常・例外を観測する
  ↓
現行境界の限界を特定する
  ↓
目的・責任・ポート・プロトコルを再照合する
  ↓
新しい正常処理へ組み込む
  ↓
監査系の盲点を再検査する
```

境界更新は、例外を標準へ吸収することだけではない。

異常を例外として残すこと、ポートを分離すること、処理を停止すること、目的を修正することも含む。

## 11. Boundary CAの実装

真理の経営学における境界CAは、組織内では次の構造へ落ちる。

| 境界CAの問い | 組織実装 |
|---|---|
| 誰が疲弊したか | 負荷指標、面談、異議申立て、離脱履歴 |
| 何が不可視化されたか | 例外記録、未分類入力、監査の監査 |
| どこへコストが移ったか | 外部化先、待機時間、無償労働、環境負荷 |
| どの責任境界が曖昧か | 許可・設計・監督・説明・停止の役割表 |
| どの返路が失われたか | Appeal Port、再審査、原目的へのエスカレーション |
| 何を修正できるか | 手順、境界、指標、共有、目的、停止 |

境界CAを成立させるには、観測だけでは足りない。

次が必要である。

1. 問題を受け取るポート
2. 履歴を保持する仕組み
3. 再判断する責任主体
4. 変更可能な権限
5. 停止可能な権限
6. 第一義へ返す経路

監査結果を記録しても、権限、指標、目的を変えられなければ、CAは儀式化する。

---

## 12. 外部化・残差・残渣

組織は、内部で処理できない負荷を外部へ押し出すことがある。

外部化そのものが常に悪いわけではない。

分業、委託、廃棄、排出、保険、移転は、社会運用に必要な場合がある。

問題は、外部化した負荷と責任の返路が失われることである。

### 12.1 Residual / 残差

残差とは、現行の分類、説明、プロトコルでは閉じきれないが、再照合可能な差分である。

残差は、新しい分類、例外処理、境界更新の候補になる。

### 12.2 Residue / 残渣

残渣とは、処理後も身体、制度、関係、環境、記号、未来に沈殿し、作用し続ける履歴的負荷である。

残渣は、処理済みという記録によって消えない。

### 12.3 外部化の照合

少なくとも次を確認する。

- 何を外部化したか。
- なぜ内部で処理しなかったか。
- 誰が外部化を決めたか。
- 誰が負荷を受けたか。
- 補償、説明、異議、修復の返路があるか。
- 時間を置いて返る負荷を追跡しているか。
- 外部化によって第一義が変質していないか。

組織のネゲントロピーは、内部秩序だけでは評価できない。

内部を整えるために外部へ過大な残渣を押し出しているなら、その秩序は局所的であり、境界CAを通過していない。

---

## 13. Diplomacy and Gateway / 外交とゲートウェイ

外交は、国家だけに存在する機能ではない。

企業、行政、病院、大学、OSS、研究組織、共同体の間にも、異なる責任境界を接続する外交機能がある。

外交とは、相手を内部化することではない。

また、相手へ完全同期することでもない。

異なる境界、履歴、目的、制約を保持したまま、通信可能性を失わないためのポート管理である。

### 13.1 Gateway / ゲートウェイ

ゲートウェイは、異なるプロトコルを持つ境界間で、通信を翻訳し、経路を調整する。

組織外交では、次が必要になる。

- 相手の責任境界の確認
- 用語と目的の翻訳
- 非共有領域の明示
- 権限と停止条件の確認
- 履歴と合意の保存
- 破棄、撤退、再交渉の経路
- 翻訳不能残差の保持

### 13.2 平和との接続

平和を、競争の完全な消滅として扱わない。

異なる存在相が、境界と履歴を保持したまま、破壊的な同期へ陥らず相互作用を継続できる状態として読む。

そのためには、違いを消すのではなく、ポート、プロトコル、外交、返路を設計する必要がある。

---

## 14. 多重境界と規模

組織境界は一枚ではない。

個人、役割、部署、企業、業界、自治体、国家、国際組織は、入れ子または重なり合う境界として存在する。

一人の人間も、職務、家庭、専門職、地域、創作、研究など複数の境界に属する。

### 14.1 境界の一意化

すべてを単一の目的、指標、権限へ圧縮すると、異なる存在相が一つの競争空間へ押し込まれる。

教育、ケア、研究、芸術、家庭、産業を同じ尺度だけで評価すれば、それぞれの第一義と時間射程が失われる。

### 14.2 境界の分裂

境界を細分化しすぎると、誰も全体責任を持たない。

各部署が自分の指標を達成していても、利用者の経路全体が破綻することがある。

### 14.3 境界間契約

多重境界の安定には、次が必要である。

- 責任の分担
- ポートの接続
- エスカレーション
- 履歴の受渡し
- 競合目的の調停
- 境界間の停止条件
- 全体へ返す監査経路

---

## 15. AIへの実装

AIは、組織境界の外側にある中立な道具ではない。

入力、履歴、権限、出力、評価、責任の経路へ接続された時点で、組織境界の一部として機能する。

AI導入で重要なのは、性能だけではない。

- どのポートから入力を受けるか。
- どの履歴へアクセスできるか。
- 何を出力できるか。
- 出力は提案か、判断か、実行命令か。
- 誰が照合するか。
- 誰が異議を受けるか。
- 誰が停止できるか。
- どのログを残すか。
- どの責任境界へ返すか。

### 15.1 AI Portの最小仕様

| 項目 | 確認内容 |
|---|---|
| Input Boundary | 入力可能な情報、個人情報、機密、外部データ |
| Model Authority | 要約、分類、提案、判断、実行のどこまで許可するか |
| Human Review | 誰が、どの条件で照合するか |
| Uncertainty | 不確実性、根拠不足、競合情報をどう示すか |
| Appeal | 利用者または対象者が異議を申し立てられるか |
| Logging | 入力、出力、モデル、設定、判断主体を何として残すか |
| Escalation | 高リスク、例外、矛盾を誰へ返すか |
| Stop / Withdrawal | 停止、ロールバック、撤退が可能か |
| Responsibility Return | 最終的な説明・改善責任がどこへ戻るか |

### 15.2 判断場維持

AIを境界機能として評価するとき、正答率だけでは足りない。

利用者が、次を保持できるかを問う。

- 選択肢
- 根拠
- 不確実性
- 保留
- 異議申立て
- 撤回
- 人間への返路
- 自ら判断する能力

AIが高速で正しい答えを返しても、人間の判断場、責任境界、異議の返路を消すなら、組織境界上の有用性は限定される。

### 15.3 DSSIとの接続

DSSIは、入力前警告、送信制御、履歴保持、保留、切断、責任返路によって、デジタル環境における判断場を維持する実装候補として読める。

ただし、本稿はDSSIの技術仕様そのものではない。

組織境界モデルが、何を実装可能な境界機能として要求するかを示す。

## 16. 通信ネットワークとの通約

本稿は、組織を通信ネットワークへ還元しない。

しかし、一定の構造通約は可能である。

|---|---|
| 組織 | Node / Administrative Domain |

| 監査 | Monitoring / Audit |

ネットワーク類比は、通信条件を明示し、シミュレーション可能な構造へ落とすために用いる。

## 18. 適用照合例

以下は、本モデルを証明する事例ではない。

異なる種類の負荷を与え、概念の作動条件と死角を確認するための照合例である。

### 18.1 行政委託

窓口、システム、問い合わせ対応を委託しても、行政目的、説明、例外、改善、停止の責任境界は行政側へ戻る。

### 18.2 OSS

コード作成やレビューが分散しても、リリース、互換性、セキュリティ対応には責任境界が必要である。

### 18.3 AI導入

分類、要約、提案をAIへ委託しても、入力条件、権限、照合、異議、撤退、説明を組織境界へ残す必要がある。

### 18.4 関税

関税は、国家境界上の交換ポート制御として読むことができる。

問題は、開放か遮断かだけではない。

どの交換を、どの条件で通し、どの産業、雇用、安全保障、消費者負担を、どの責任境界で引き受けるかである。

### 18.5 平和設計

異なる組織、国家、共同体を一つへ統合するのではなく、境界、外交ポート、翻訳、停止、再交渉の返路を保持する。

### 18.6 異常制御

正常を仕組みに委ね、逸脱を観測し、成功している異常と監査系の盲点を境界更新へ戻す。

## 19. 組織境界の失敗類型

### 19.1 Boundary Ambiguity / 境界曖昧化

内部、外部、責任、停止権限が分からない。

### 19.2 Boundary Rigidity / 境界硬直

外部差分、例外、異議を受け取れない。

### 19.3 Port Collapse / ポート崩壊

異なる通信を一つの窓口へ集中し、処理不能になる。

### 19.4 Port Absence / ポート不在

苦情、例外、異議、学習を受け取る公式経路がない。

### 19.5 Responsibility Dilution / 責任希釈

分業、委託、自動化によって、誰も全体を引き受けない。

### 19.6 Protocol Absolutization / プロトコル絶対化

手続に入らない現実を存在しないものとして扱う。

### 19.7 Logging without Return / 返路なき記録

ログは蓄積するが、改善、説明、境界更新へ接続されない。

### 19.8 Audit Ritualization / 監査儀式化

監査は行うが、権限、指標、目的を変えられない。

### 19.9 Single-Metric Compression / 単一指標圧縮

異なる目的、存在相、時間射程を一つの数値へ圧縮する。

### 19.10 Successful Anomaly / 成功している異常

成果の背後にある属人化、疲弊、外部化が異常として認識されない。

### 19.11 Responsibility Laundering / 責任洗浄

利益と権限を保持する主体が、負荷と説明だけを下流へ送る。

### 19.12 False Closure / 偽閉鎖

手続完了、指標達成、同意取得を、責任と修正の完了として扱う。

## 20. 非主張境界

本稿は、次を主張しない。

- 組織を通信ネットワークと同一視する。
- 企業、行政、国家、個人、AIが同じ存在であるとする。
- ネゲントロピーを熱力学的な測定量として組織評価へ直接用いる。
- 法的責任、行政責任、医療責任を本稿だけで判定できる。
- 特定の組織構造、政策、関税率、AI製品、経営手法を推奨する。
- ポート設計だけで組織の倫理性や安全性を保証できる。
- 監査、ログ、自動化を増やせば責任問題が自動的に解決する。
- 人間を組織または機械へ還元する。
- 本稿を、人事評価、思想診断、人格分類、監視強化の正当化に使ってよい。

本稿が主張するのは、次である。

- 共有された目的は、責任、通信、履歴、例外、停止条件へ実装されなければならない。
- 組織は、何を受け取り、何へ変換し、何を返す境界であるかによって読める。
- 機能の委託は、設計、許可、監督、説明、改善の責任を消去しない。
- ポートとプロトコルは、差分を受け取る条件と返路を観測可能にする。
- 異常、例外、残差、残渣は、境界更新の入力になりうる。
- 組織の内部秩序は、外部化された負荷を含めて境界CAを受けなければならない。

## 22. 暫定結論

目的は、掲げただけでは実装されない。

目的は、組織境界を作り、責任を配置し、ポートを開き、プロトコルを定め、履歴を残し、例外を処理し、停止と修正の返路を持ったとき、初めて運用可能になる。

組織とは、内部を守る壁ではない。

何を受け取り、何へ変換し、何を返し、どの負荷を自らの責任として引き受けるかを定める境界である。

機能は委託できる。

責任は、委託によって消すことはできない。

正常は仕組みに委ねることができる。

しかし、異常、例外、残差、残渣は、組織がどこで現実に追いつけなくなったかを示す。

したがって、組織の成熟は、正常を止めないことだけでは測れない。

異常を受け取り、責任境界へ返し、目的、境界、ポート、プロトコルを更新できるかによって測られる。

```text
第一義
  ↓
組織境界
  ↓
責任境界
  ↓
ポートとプロトコル
  ↓
履歴・監査・異議申立て
  ↓
異常・残差・残渣
  ↓
境界更新
  ↓
境界CA
  ↓
第一義の再照合
```

これが、存在境界論における、組織境界・責任境界・ポートへの実装である。
